# symbiont-engine — всё включено и безопасно (защита встроена, не выключением)

## Принцип: безопасно ≠ выключено
Все функции РАБОТАЮТ по умолчанию. Безопасность встроена в саму реализацию:
- АКТИВНАЯ ДИАГНОСТИКА — пробы на ИЗОЛИРОВАННЫХ соединениях (отдельные сокеты),
  твой живой трафик не трогают. Провал пробы браузер не заметит. ВКЛ по умолч.
  Лог [диагностика]: «youtube.com → SNI-блокировка», «discord.media → работает» и т.д.
- KYBER-ДЕСИНК — для многопакетного ClientHello (Chrome 124+) впрыскиваем
  fake-decoy (реальный google ClientHello, низкий TTL), а РАЗБИТЫЙ ПАКЕТ НЕ
  ТРОГАЕМ. Работает (DPI отравлен) и безопасно (реальные данные целы). Лог [kyber].
- QUIC-ДЕСИНК — реальный QUIC Initial (google) как fake, валидным пакетом с
  низким TTL + repeats (как zapret), реальный пакет не трогаем. (Активен в
  режиме --quic=desync; по умолч --quic=pass, чтобы точно не ломать QUIC-сайты.)
- A+B САМОЛЕЧЕНИЕ — при перегрузке канала (рост ошибок отправки) движок САМ
  снижает интенсивность обхода (меньше repeats), при норме восстанавливает.
  НЕ МОЖЕТ уронить сеть (только убавляет СВОЮ активность). Лог [канал].
- FAIL-OPEN — любая паника обработки → пакет уходит как есть (инет не рвём).

## Включено по умолчанию (безопасно)
вариант C (--auto-detect), детект по входящему RST (--watch-inbound),
autottl, активная+пассивная диагностика (--diagnose), голос Discord (--voice),
A+B самолечение (всегда), fail-open (всегда), kyber-safe (всегда).
Осознанно ВЫКЛ (могут ослабить/ломать): --randomize (ослабляет обход),
--quic=desync (может ломать QUIC-сайты), --tlsrec (альтернативная техника).

## Запуск (админ, Bebra ВЫКЛ, DoH оставь)
```powershell
cd Z:\symbiont-engine
.\symbiont-engine.exe --log=engine.log --reprobe
```
Всё нужное уже включено. Если что-то не так — закрой окно (Ctrl+C), WinDivert
отключится, трафик пойдёт напрямую. Рядом: .exe + WinDivert.dll + WinDivert64.sys.

## Что в логах (всё всё, понятно)
[диагностика] <домен> → SNI-блок / нет ответа (IP-блок→туннель) / работает
[auto] вердикт: <домен> ЗАБЛОКИРОВАН → обход
[kyber] kyber ClientHello: впрыснул fake-decoy (реальный пакет не трогаю)
[autottl] RST от <ip>: TTL=.. → TTL фейка≈.. (где стоит ТСПУ)
[канал] перегрузка → снижаю интенсивность до N% / восстанавливаю
[recover] паника → пакет как есть (инет цел)
[voice] [tlsrec] [диагноз] [сводка] (вх.RST/вх.данные)

## Что внутри полностью реализовано
1. Вариант C (наблюдение + обход только заблокированного, не трогая рабочее).
2. Детект блокировки: исходящие ретрансмиссии + входящий RST.
3. Активная диагностика (изолированные TCP/TLS-пробы → тип блокировки).
4. autottl (TTL фейка по ответному RST).
5. Многофазность как zapret (google 681+ip-id=zero; общие сайты свой seqovl).
6. Реальные пакеты zapret (TLS/QUIC/STUN) + узкие порты голоса + реальный bin-fake.
7. TLS-record фрагментация (--tlsrec).
8. Kyber-десинк через fake-decoy (безопасно).
9. QUIC-десинк реальным bin (в режиме desync).
10. A+B самолечение + fail-open + kyber-safe.

## Граница честности
НЕ обещаю «идеально с первого раза» на твоём ТСПУ — этого не может никто. Что
честно: всё перечисленное РЕАЛИЗОВАНО и КОМПИЛИРУЕТСЯ чисто (vet ок, PE32+),
безопасность встроена (изоляция проб / реальные данные не трогаем / самолечение
только убавляет своё / fail-open). Доводка значений (autottl, классификация,
помогает ли что) — по ТВОИМ логам. Очень жду их.

## НОВОЕ: автосписок заблокированных (autohostlist) — память варианта C
Обнаруженные заблокированные домены теперь СОХРАНЯЮТСЯ в symbiont-blocked.txt
(рядом с .exe) и подхватываются при старте — обходятся сразу, без повторного
обучения. Файл текстовый, по домену на строку, # = комментарий — можешь
ДОБАВЛЯТЬ свои домены ВРУЧНУЮ. Лог [hostlist]: «автосписок: + X».

## IPv6 — РЕАЛИЗОВАН (безопасно)
IPv6+TCP теперь поддержан: для заблокированных доменов впрыскивается fake-decoy
(реальный google ClientHello, низкий hop limit), а РЕАЛЬНЫЙ IPv6-пакет всегда
уходит как есть — IPv6-связность не сломается. Вариант C видит и IPv6-домены.
IPv6-UDP (QUIC) пока просто пробрасывается.

## QUIC frame splitting — РЕАЛИЗОВАН и проверен (RFC 9001)
Полностью реализовано: расшифровка QUIC Initial (HKDF + AES-128-GCM + header
protection), разрез ClientHello на 2 CRYPTO-фрейма внутри SNI, повторное
шифрование. Деривация ключей СВЕРЕНА с тест-векторами RFC 9001, и round-trip
проверен на РЕАЛЬНОМ QUIC Initial: сервер получает идентичный ClientHello, DPI
видит 2 фрейма и не собирает SNI. Флаг --quic-split (ВКЛ). Безопасно: режем
только заблокированные домены, при любой ошибке исходный пакет уходит как есть
(QUIC не ломается), работает даже в режиме --quic=pass.


## НОВОЕ: полный набор техник
Fooling-режимы (--fooling): badsum, badseq, datanoack, md5sig, ts, none.
  (hopbyhop не реализован — он IPv6-специфичный и нишевый.)
Стратегии (--strategy): split, disorder, fake, fakeddisorder, multisplit,
  multidisorder, oob. multisplit/multidisorder рвут SNI на НЕСКОЛЬКО сегментов.
  oob — out-of-band (URG) фейк с низким TTL (безопасно: реальные данные целы).
IPv6: теперь и ВХОДЯЩИЙ детект (RST/данные для варианта C), и QUIC frame
  splitting по IPv6. Реальный IPv6-пакет по-прежнему всегда уходит как есть.

## Автообнаружение — ДА, это ядро (подтверждение)
Вариант C автоматически понимает, что заблокировано (по ретрансмиссиям +
входящему RST), и применяет обход ТОЛЬКО к этому, не трогая рабочее. Это уже
работает. Активная диагностика дополнительно классифицирует тип блокировки.

## НОВОЕ: hopbyhop + единая логика решений
- hopbyhop (--fooling=hopbyhop): IPv6 Hop-by-Hop заголовок в fake-decoy — DPI не
  идёт по цепочке заголовков и не видит TCP. Полный набор fooling теперь:
  badsum, badseq, datanoack, md5sig, ts, hopbyhop, none.
- ЕДИНАЯ ЛОГИКА РЕШЕНИЙ (decision.go) — в одном месте, явно, ВСЕ случаи:
    1. исключения (апдейтер/CDN/служебное) → НЕ трогаем никогда
    2. нет SNI → наблюдаем
    3. kyber-ClientHello → только безопасный fake-decoy
    4. список заблокированных (встроенный+автосписок+ручной) → обход
    5. вердикт варианта C: blocked→обход, working→не трогаем
    6. неизвестно → наблюдаем, пока не доказана блокировка
  С --diagnose видно в логе [решение]: «<домен> → ОБХОД/не трогаю (причина)».

## ЗАКРЫТЫ ДЫРЫ (продуманы все варианты событий)
1. ЭСКАЛАЦИЯ техник: если обход домен не пробил (RST/ретрансмиссии продолжаются),
   движок САМ переключается на следующую технику из таблицы (8 техник, простое→
   агрессивное), с гистерезисом (не чаще раза в 8с). Лог [auto]: «обход для X не
   пробил → переключаю технику #N». Это circular-логика как у zapret.
2. ГИСТЕРЕЗИС: вердикт/техника не дёргаются — смена не чаще раза в 8с.
3. ФРАГМЕНТЫ IP: фрагментированные пакеты безопасно пропускаются (не режем —
   у фрагмента нет полного TCP-заголовка).
4. KYBER: многопакетный ClientHello — безопасный fake-decoy, не режем.
5. СБРОС вердикта: поведенческие вердикты протухают через 6ч (авто-перепроверка);
   persistent (автосписок/ручные) — не протухают.
6. ЕДИНАЯ ЛОГИКА (decision.go) — все случаи в одном месте, с причиной в лог.

## ОСТАЛИСЬ НЕ закрытыми (честно, требуют логов/нишевые)
- Детект «ТСПУ ушёл в bypass» (всё открылось) — чтобы не тратить CPU. Сложно
  отличить от «наш обход работает» без проб без обхода. Нужны логи.
- Конфликт с одновременно включённым туннелем (Bebra) — не детектируем.
- HTTP/80 Host-десинк — фокус на HTTPS/SNI (основной случай).
Эти три — после твоих логов (видеть реальное поведение твоего ТСПУ).

## ПЕРЕСТРОЕНО: работает как zapret — сразу, без твоей настройки
Главный принцип (как ты просил — автоматически под любой провайдер/ТСПУ):
- ИЗВЕСТНОЕ ЗАБЛОКИРОВАННОЕ (YouTube/Discord/Telegram/Instagram и весь список)
  обходится СРАЗУ, не дожидаясь детекта, ЭТАЛОНОМ zapret (техника #0:
  fake+seqovl=681+ip-id=zero, реальный google-пакет). Это копия рабочего
  general.bat — максимальный шанс пробить ту же сеть, что пробивает zapret.
- Если #0 не пробил — АВТО-ЭСКАЛАЦИЯ по 8 техникам (как circular zapret),
  после полного круга → «нужен туннель» (IP-блок).
- ВАРИАНТ C — надстройка для НЕизвестных доменов (ловит то, чего нет в списке).
- АКТИВНАЯ ДИАГНОСТИКА на старте (изолированные пробы) сама анализирует, что и
  как блокируется у тебя — без твоего участия.
Итого: детект НЕ обязателен для известного — оно обходится сразу. Детект нужен
лишь чтобы РАСШИРИТЬ список под твою сеть автоматически.

## Десктопные приложения — да, обходим (app-agnostic)
Движок работает на уровне ПАКЕТОВ (WinDivert), не приложений — ему всё равно,
кто шлёт трафик. Любое приложение с TLS-ClientHello (заблокированный SNI) на
наших портах обходится автоматически.
Порты по умолчанию = набор zapret: 443, 2053, 2083, 2087, 2096, 8443
  (ловим в т.ч. Discord media/voice по TCP, не только браузер).
Обходим: браузеры, Discord (API+голос+media), Steam/игры на TLS, Instagram/
  Twitter/TikTok десктоп, Telegram в FakeTLS/web-режиме.
НЕ берётся локально (природа протокола, не недоработка):
  - Telegram-десктоп на ОБЫЧНОМ MTProto (нет TLS/SNI для разреза) → нужен
    встроенный MTProto-прокси Telegram или туннель;
  - всё, что блокируется по IP дата-центров → нужен туннель.

## MTProto (Telegram-десктоп) — РЕАЛИЗОВАН локально
Флаг --mtproto (ВКЛ). У MTProto нет SNI, поэтому десинк по-другому: ловим
соединения к IP дата-центров Telegram (публичные диапазоны вшиты) и рвём
СИГНАТУРУ первого пакета (split+fake, disorder-порядок) — ТСПУ не матчит MTProto,
сервер собирает по TCP, fake умирает по TTL. Реальные данные не трогаем.
Лог [mtproto]: «Telegram DC X: разорвал сигнатуру MTProto».
Помогает, ЕСЛИ Telegram режут по DPI-сигнатуре (частый случай в РФ).
НЕ поможет, если блок по IP дата-центров (тогда нужен туннель) — увидим по логу.
Ловим MTProto на порту 443 (дефолт Telegram); порты 80/кастомные могут не
попасть в фильтр.

## Правка от 2026-06-26 (вторая): Discord-QUIC ловим ПО IP

Прошлая версия роняла Discord-QUIC только по SNI из QUIC-Initial. Но QUIC-Initial

клиент уходит на TCP, где обход уже работает. discord.media (голос) по-прежнему
не трогаем. В логе: [quic] Discord по QUIC уронен (IP … = Discord по TCP-CH).

ЕСЛИ всё ещё висит — гарантированный фолбэк (как тест с фаерволом): запусти с
флагом `--quic=drop` (глушит ВЕСЬ QUIC, видео уходит на TCP — работает, чуть
медленнее). Это 100% эквивалент блокировки UDP/443 в фаерволе.

## Правка от 2026-06-26 (шестая, РЕШЕНИЕ Discord): IP-слой обхода (аналог ipset-all zapret)

КОРЕНЬ (по анализу всех 8 логов): на discord.com/discord.gg, которые движок
обходит по видимому SNI, RST=0 и silent=0 — они работают, данные идут. Но Discord
всё равно не грузится, потому что часть соединений он открывает через Cloudflare с
ECH (без видимого SNI). Движок их по SNI не видел → они шли МИМО обхода и резались
ТСПУ (отсюда «чат/настройки/гейтвей не грузятся»). zapret это закрывает правилом
ipset-all (десинк по IP, без разбора SNI) — у нас такого слоя не было.

видел discord.com как «обходится» (ОБХОД✓) и считал, что всё хорошо.

ИСПРАВЛЕНО: движок теперь РОВНО ОДИН РАЗ на каждый подтверждённый Discord-IP рвёт
СТАРЫЕ установленные соединения к нему → десктоп переподключается, новое
рукопожатие идёт через обход. Свежие (уже обойдённые) соединения после этого не
трогаются — Discord не мигает. Работает в связке с IP-слоем (ECH) из прошлой
правки.

## Правка от 2026-06-26 (десятая, КОРНЕВОЙ ФИКС): резет соединений Discord по PID

ПРИЧИНА всей нестабильности гейтвея (604 vs 19 пакетов, «сообщения/настройки не
грузятся»): движок стартует, когда Discord УЖЕ запущен и держит соединения,
открытые ДО обхода — на «мёртвом» пути. Десинк лечит только новое рукопожатие, а
старый гейтвей висит и не достреливает READY. zapret этого не знает, потому что
стартует службой ДО Discord — у него все соединения свежие.

РЕАЛИЗОВАНО: точное определение процесса Discord по PID (Toolhelp snapshot) и
разрыв ИМЕННО его стартовых соединений:
- При старте движка (через 1.5с) один раз находим все established-соединения
  процессов Discord.exe по PID-владельцу сокета и рвём их (захват стартового
  набора). Discord переподключает всё свежим → новые рукопожатия идут через обход
  → гейтвей достреливает READY → сообщения/настройки грузятся.
- Соединения, появившиеся ПОСЛЕ захвата, уже свежие/обойдённые — их не трогаем
  (без мигания). Точно по PID, без гадания по IP (нет задевания чужого Cloudflare).
- Работает в обе стороны: движок до Discord (всё свежее, резетов нет) ИЛИ Discord
  до движка (стартовые соединения разорваны → переподключение через обход).

как обычно: .\symbiont-engine.exe --log=engine.log — Discord можно не закрывать.

## Правка от 2026-06-26 (одиннадцатая): Discord-QUIC всегда фейкуем (фикс сообщений)

НАЙДЕНА вероятная причина «гейтвей дотянулся, а сообщения/настройки не грузятся».
applyQUICDesync имел оптимизацию: «не фейковать QUIC к РАБОЧИМ хостам» (чтобы не
замедлять рабочий трафик). Но TCP-путь Discord помечается как РАБОЧИЙ (ОБХОД✓) →
поэтому движок НЕ фейковал QUIC Discord. А Discord грузит сообщения/настройки/
контент (cdn.discordapp.com, API) по QUIC/HTTP3 — и этот незафейканный QUIC ТСПУ
режет/душит. В логе: QUIC=17131 пакетов, при этом cdn.discordapp.com вообще нет в
TCP — значит контент идёт по QUIC. zapret фейкует Discord-QUIC ВСЕГДА.

ИСПРАВЛЕНО (аддитивно, без регрессий): для Discord-IP фейк QUIC больше не
пропускается оптимизацией «рабочий хост» — Discord-QUIC фейкуем всегда, как zapret.
Реальный пакет по-прежнему проходит; фейк (google QUIC, низкий TTL) до сервера не
доходит. YouTube/прочий QUIC не затронут. В логе: [quic] Discord-QUIC фейкуем.

Запуск как обычно: .\symbiont-engine.exe --log=engine.log
