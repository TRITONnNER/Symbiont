# Симбионт — «Баланс активного времени»: полная реализация

Фича с картинки: **оплата по факту, тир Premium**. Пакеты часов — 100 ч = 149 ₽ (≈1,49 ₽/ч),
300 ч = 399 ₽ (≈1,33 ₽/ч). Обещание: *«Пакет часов не привязан к календарю: время идёт
только под подключением и не сгорает по дате. Остаток всегда виден в аккаунте.»*

Это разбор того, что уже есть в коде, чего не хватает для боевой работы, и как довести до конца.

## 2. Чего НЕ хватает для боевой работы (главное)

| # | Дыра | Почему критично |
|---|---|---|
| **A** 🔴 | **Нет метеринг-агента на узле.** `/v1/node/session` никто реально не вызывает — `grep` по `server/`, `engine/`, `platform/` пуст. Endpoint есть, «звонящего» нет. | Без него баланс **никогда не списывается** в бою → часы = бесплатный безлимит. |
| **B** 🔴 | **Нет enforcement при нуле.** Ничто не рвёт туннель, когда минуты кончились. | Пользователь с 0 ч продолжает пользоваться бесплатно. |
| **C** 🔴 | **Нет идемпотентности / crash-safety.** Узел шлёт «сырые» `minutes` одним куском. Ретрай сети = двойное списание; падение узла = потеря всей сессии или переплата. | Прямые потери денег/доверия в обе стороны. |
| **D** 🟡 | **Не определён приоритет «подписка vs часы».** При активной подписке часы не должны тратиться. | Иначе у платящих подписчиков «съедаются» часы. |
| **E** 🟡 | Нет предупреждений о низком остатке и живого счётчика при подключении. | UX-обещание «остаток всегда виден». |
| **F** 🟡 | Возврат/сгорание неиспользованных часов не определены. | Юр. и «не сгорает по дате». |
| **G** 🟡 | 300 ч в flutter-UI (в вебшелле уже обе карточки), Ultimate-баланс, крипто-скидка в цене. | Мелкие доделки/решения. |

## 3. Модель учёта (ключевое инженерное решение)

**Единица** — активная **минута под подключением** (wall-clock узла), не объём трафика.

**Кто считает — УЗЕЛ, не клиент.** Клиент недоверенный (его можно пропатчить). Узел уже
подписывает отчёт HMAC-секретом. Клиент только *отображает* остаток.

**Инкрементально, а не одним куском в конце.** Узел шлёт отчёт каждые **N минут (реком. 5)**
в течение сессии, а не только при disconnect. Тогда падение узла теряет максимум N минут
(в пользу пользователя), а не всю сессию.

**Идемпотентность через кумулятивный счётчик (самый простой crash-safe вариант):**
- Узел на каждую сессию держит `session_id` и шлёт **накопленные** минуты сессии `cum`.
- Сервер хранит `charged[session_id]` и списывает только разницу:
  `delta = max(0, cum − charged[session_id]); charged[session_id] = cum`.
- Повтор того же `cum` → `delta = 0` (двойного списания нет). Пропущенный отчёт наверстывается следующим `cum`.

**Округление — в пользу пользователя.** Считать в секундах, списывать поминутно по факту
накопления ≥ 60 с. Не округлять вверх каждый интервал (иначе набегает лишнее).

**Несколько устройств.** Баланс — на аккаунт; Premium = без лимита устройств. Две параллельные
сессии (разные `session_id`) списывают суммарно — это честно (пользователь реально жжёт два канала).
Явно задокументировать: часы идут по каждому активному подключению.

## 4. Enforcement при нуле (обязательно)

**Авторизация на старте сессии — новый endpoint `POST /v1/node/authorize`:**
- Узел спрашивает: `{node_id, account_id}` (подпись узла).
- Сервер отвечает: `{allowed: bool, session_token, lease_minutes}`.
  - `allowed=false`, если `mode=balance` и `active_minutes_left ≤ 0` и нет активной подписки → узел **не поднимает** туннель, клиент видит «часы закончились».
  - `session_token` — привязан к `(node_id, account_id, session_id)`; **только он** даёт право списывать этот баланс (защита от чужого узла, см. §7).
  - `lease_minutes = min(remaining, 30)` — «лизинг»: сколько узел может открутить **без связи с backend** (оффлайн-устойчивость). Больше лиза узел не даёт даром.

**В процессе.** Ответ `/v1/node/session` уже возвращает `active_minutes_left`. Когда ≤ 0 →
узел завершает сессию с grace-периодом 1–2 мин (мягкий разрыв, не резкий).

**Оффлайн.** Если backend недоступен, узел режет по локальному `lease_minutes` из последнего
`authorize`. Достучались снова — обновили лиз. Так узел не может «подарить» безлимит при обрыве связи с billing.

## 5. Приоритет «подписка vs часы»

Баланс часов — это **резерв**, а не замена подписки.
- Если у аккаунта активна подписка (`days_left > 0` или `lifetime`) → часы **не списываются**
  (в `/v1/node/session` charge только при `days_left == 0 && !lifetime`).
- Покупка часов **не обнуляет** `days_left`. `mode` должен допускать сосуществование:
  сначала тратятся дни подписки, часы включаются, когда подписка истекла.
- Правка в `_sub`/`node_session`: списывать минуты только когда подписка не покрывает.

## 6. Клиент (UX)

- **Живой счётчик остатка** при активном подключении (обратный отсчёт), синхронный со `status`.
- **Пороговые предупреждения:** 30 / 10 / 5 мин → тост + быстрая кнопка «докупить».
- **При нуле:** мягкий disconnect + экран «Часы закончились» с кнопкой «Купить пакет».
- Карточки **100 ч и 300 ч** (в вебшелле уже обе; в flutter `tariffs_screen` добавить 300 ч — `PRICING.md` todo #3).
- **Крипто-скидка −10 %** применять к отображаемой цене и сумме при `method=crypto` (`PRICING.md` todo #2).
- Опционально: **авто-докупка** при остатке < порога (галка в аккаунте) — удобно, но требует сохранённого метода оплаты; можно во вторую очередь.

## 7. Анти-абуз

- **Списывать может только владелец сессии.** Сейчас любой валидный узел может слать `minutes`
  на любой `account_id`. Ввести `session_token` из `authorize`, привязанный к `(node, account, session)` —
  без него `/v1/node/session` отклоняется. Иначе злонамеренный/скомпрометированный узел
  сливает чужой баланс.
- **Sanity-cap:** списанные минуты за интервал ≤ (реальный интервал wall-clock × число активных сессий) + запас. Абсурдные значения → лог + отказ.
- HMAC-подпись узла уже есть (`server.py:764–767`) — оставить.

## 8. Возврат и сгорание

- «Не сгорает по дате» — **без TTL** у баланса (уже так). Отразить в Условиях.
- Рекомендуемая политика возврата: **полный возврат, если использовано 0 минут в течение 14 дней;
  после первой активной минуты пакет невозвратен** (расходник). Согласовать с общим сроком возврата сайта.

## 9. Ultimate-баланс — решение

Рекомендую **пока не вводить**. Баланс — это лёгкий вход на Premium-фичи по факту; Ultimate
(max-скорость, выделенный IP) логичнее продавать подпиской. Лишний SKU только запутает витрину.

## 11. Тест-план (расширить `selftest_billing.py`)

1. authorize выдаёт `session_token` и `lease`; без токена `/node/session` = 403.
2. Кумулятивное списание идемпотентно: повтор того же `cum` не списывает второй раз.
3. Падение узла между отчётами: следующий `cum` наверстывает, переплаты нет.
4. Ноль баланса → `authorize.allowed=false`; активная сессия завершается с grace.
5. Приоритет подписки: при `days_left>0` часы не тратятся.
6. Два устройства одновременно списывают суммарно.
7. Оффлайн: узел режет по `lease_minutes`, не больше.

### Итог
Экономика и хранение баланса **готовы и покрыты тестами**. Чтобы фича заработала в бою,
нужны три вещи в порядке важности: **(A) метеринг-агент на узле**, **(B) enforcement при нуле**,
**(C) идемпотентно-кумулятивное списание с `session_token`**. Всё остальное — UX-полировка и решения.
```
authorize → [сессия] → session(cum) каждые 5 мин → 0 → grace → disconnect
   │                        │                                     │
   выдаёт lease+token   идемпотентное списание           экран «часы кончились» + купить
```
