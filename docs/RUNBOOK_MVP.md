# Симбионт — ранбук MVP: от VPS до первого реального подключения

Пошагово: арендовать сервер → 3 команды → создать реальный аккаунт → подключиться.
Плюс: где данные, где логи, что делать если «отвалился интернет».

> Всё, кроме живого прогона на VPS/Windows, проверено автотестами (19 наборов).
> Этот документ — как довести до реального сервиса на вашей инфраструктуре.

---

## 0. Что понадобится (≈300–500 ₽/мес)

| Что | Зачем | Ориентир |
|---|---|---|
| **VPS вне РФ**, Ubuntu 22.04/24.04, 1 vCPU / 1 ГБ | узел выхода + бэкенд | Нидерланды/Финляндия/Германия; ~300 ₽/мес |
| Публичный IP | Reality работает по IP, домен не обязателен | выдаётся с VPS |
| SSH-доступ (root) | развернуть | пароль или ключ от провайдера |

> ⚠️ Узел выхода **в РФ ставить нельзя** (юр-предохранитель это блокирует). РФ допустим
> только как `relay` (перевалка, не точка выхода).

## 1. Три команды (Server-in-a-Box)

На своей машине — скопировать проект и запустить установщик:

```bash
# 1) залить проект на сервер
scp -r symbiont_build/ root@<IP_СЕРВЕРА>:/root/

# 2) зайти на сервер
ssh root@<IP_СЕРВЕРА>

# 3) поднять ВСЁ одной командой (узел + бэкенд, авто-настройка, само-починка)
cd /root/symbiont_build/server && sudo bash bootstrap_vps.sh
```

Что произойдёт само (см. `server/README.md`):
- **авто-подбор**: страна по IP, самый быстрый живой SNI, протоколы, стартовая загрузка;
- ставится **sing-box** (Reality/Hysteria2/SS2022), systemd, firewall;
- поднимается **бэкенд** (FastAPI) на `0.0.0.0:8000`, узел вписывается в подписанный манифест;
- в конце скрипт печатает **адрес бэкенда**, **ключ подписи** и готовую команду сборки клиента.

> Разнести узел и бэкенд по разным серверам: на узле — `--no-backend --register-to https://<БЭКЕНД> --node-secret <СЕКРЕТ>`.
> Тогда узел сам зарегистрируется на центральном бэкенде и будет слать heartbeat (само-починка).

**Задать секреты (обязательно для боя)** — до запуска, через окружение systemd или `secrets.json`:
```
SYMBIONT_ADMIN_TOKEN         админ-доступ (/v1/admin/*)
SYMBIONT_NODE_SECRET         секрет регистрации узлов
SYMBIONT_WHEEL_SEED          seed колеса (provably-fair)
SYMBIONT_PAY_WEBHOOK_SECRET  подпись вебхука платежей
```
Если не задать — сгенерируются случайные и лягут в `secrets.json` (не коммитить!).

## 2. Реальные данные (настоящая БД)

Весь сервис хранит состояние в **реальной базе данных SQLite** — один файл
`symbiont_state.db` рядом с `server.py` (WAL-режим, атомарные транзакции). Аккаунты,
сессии, ключи, узлы, платежи, health, диалоги поддержки — всё там. Бэкап = скопировать
`symbiont_state.db`. Посмотреть SQL-инструментами:
```bash
sqlite3 symbiont_state.db "SELECT k FROM kv;"     # разделы состояния
```
> Переход бесшовный: старые `*.json` от прежней версии импортируются в БД один раз
> автоматически; повреждённый файл не теряется (уходит в `*.corrupt`).
> **`signing.key` (ключ подписи манифеста) — отдельный файл, держать вне git.**

Ещё более строгая схема с отдельными таблицами/индексами (`backend/db.py`: `redeem_key`
и колесо с инвариантами на уровне БД, 66 тестов) доступна как следующий уровень —
но ключевые денежные инварианты уже защищены логикой сервера и тестами.

## 3. Создать аккаунт и всё протестировать

### Через приложение (рекомендую)
Собрать клиент, указывающий на ваш сервер (команду печатает bootstrap):
```bash
cd symbiont_build
flutter build windows --release \
  --dart-define=SYMBIONT_BASE_URL=http://<IP>:8000 \
  --dart-define=SYMBIONT_PUBKEY=<КЛЮЧ_ИЗ_BOOTSTRAP>
```
Запустить `build\windows\x64\runner\Release\symbiont.exe` **от администратора**, пройти
онбординг (создаётся анонимный аккаунт + recovery-код), нажать «Подключиться».

### Через API (быстрая проверка без сборки)
```bash
API=http://<IP>:8000
# 1) создать аккаунт
TOKEN=$(curl -s -X POST $API/v1/account/anon -H 'content-type: application/json' \
  -d '{"label":"я"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
# 2) выпустить ключ (админ) и проверить его БЕЗ активации
CODE=$(curl -s -X POST $API/v1/admin/issue -H "x-admin-token: $SYMBIONT_ADMIN_TOKEN" \
  -H 'content-type: application/json' -d '{"plan":"pro","grant_days":30,"uses":1}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["code"])')
curl -s -X POST $API/v1/key/check -H 'content-type: application/json' -d "{\"code\":\"$CODE\"}"
# 3) активировать ключ
curl -s -X POST $API/v1/key/redeem -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d "{\"code\":\"$CODE\"}"
# 4) подписанный манифест с вашим узлом
curl -s "$API/v1/manifest" | head -c 400
```
Так же проверяются: `/v1/wheel/spin` (колесо), `/v1/referral`, `/v1/billing/*`, `/v1/support/*`.
Веб-чекер ключа (без сборки): открыть `symbiont_build/web/check.html?api=http://<IP>:8000`.

## 4. Логи — «что и как чинить»

Логируется **всё**: каждый запрос (метод · путь · код · время), полные трейсбеки ошибок,
и события безопасности/денег/узлов. Два места сразу:

```bash
journalctl -u symbiont-backend -f                 # живой журнал бэкенда
tail -f /opt/symbiont/backend/symbiont-backend.log # файл (ротация 5×5 МБ)
```
Уровень — `SYMBIONT_LOG_LEVEL` (`DEBUG`/`INFO`/`WARNING`). Смотреть в первую очередь на
`WARNING`+ строки:

| Строка в логе | Что значит | Что делать |
|---|---|---|
| `→ 4xx/5xx` | запрос отклонён/упал | код и путь рядом; 5xx = смотри трейсбек ниже |
| `НЕОБРАБОТАННАЯ ОШИБКА … Traceback` | баг в обработчике | файл:строка в трейсбеке |
| `отказ админ-доступа` / `неверная подпись узла` | неверный секрет | сверить `SYMBIONT_*` секреты |
| `само-починка: узлы выпали` | узел не шлёт heartbeat | проверь узел: `systemctl status sing-box-symbiont`, сеть |
| `ПОВРЕЖДЁН стор …` | битый JSON-файл | восстановить из `*.corrupt`, проверить диск |

Узел: `journalctl -u sing-box-symbiont -f` · `sing-box check -c /etc/symbiont/config.json`.

## 5. «Отвалился интернет» и другие сетевые сбои

Самый частый страх — обход/прокси ломает связь. Что заложено и что делать:

- **Локальный прокси (ByeDPI, без админа).** Приложение ставит системный прокси на
  `127.0.0.1` и **откатывает** его при отключении; при старте есть авто-восстановление
  (`_WinProxy.recover`) — если прошлый сеанс упал, прокси чинится при следующем запуске.
  Бэкап хранит **подлинное** исходное состояние (исправлено: повторное подключение больше
  не затирает бэкап «нашим» прокси, иначе после отключения интернет оставался бы сломан).
  - *Если браузеры «без интернета» после краха:* **перезапустите приложение** (оно откатит
    прокси), либо вручную: Параметры → Сеть → Прокси → выключить, ИЛИ
    `reg add "HKCU\...\Internet Settings" /v ProxyEnable /t REG_DWORD /d 0 /f`.
- **Обход с админом (winws/GoodbyeDPI, WinDivert).** Конфликт «два обхода на одном WinDivert»
  рвал сеть — устранено: пути подключения **взаимоисключающие**, каждый перед стартом делает
  `_stop()` (гасит прошлый движок, `taskkill winws.exe`). Один WinDivert-перехват в момент.
- **Kill-switch** (рвать трафик при падении связи) — на туннельном (sing-box) пути, нативно.
- *Полностью «нет интернета» и приложение закрыто:* причина почти всегда — оставшийся
  системный прокси (см. выше) или запущенный `winws.exe` (`taskkill /F /IM winws.exe`).

## 6. Чек-лист запуска

- [ ] VPS вне РФ, Ubuntu 22.04/24.04, root-доступ.
- [ ] Заданы `SYMBIONT_*` секреты (не дефолтные).
- [ ] `bootstrap_vps.sh` отработал; `systemctl status sing-box-symbiont symbiont-backend` — active.
- [ ] Порты открыты (в ufw и в панели провайдера): 443/tcp, 8443/**udp**, 9443/tcp, 8000/tcp.
- [ ] `curl http://<IP>:8000/v1/pubkey` отвечает; `/v1/manifest` содержит ваш узел.
- [ ] Клиент собран с вашим `SYMBIONT_BASE_URL` + `SYMBIONT_PUBKEY`, запущен от админа.
- [ ] Логи чистые (нет `WARNING`/`НЕОБРАБОТАННАЯ ОШИБКА`).
- [ ] На реально заблокированной сети подключение поднимается (каскад).
